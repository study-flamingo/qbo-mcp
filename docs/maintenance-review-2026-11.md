## 2. Security findings

### 🔴 S1 — OAuth tokens committed to the repository
`qbo_tokens.json` was **tracked in git** at three paths:

```
qbo_tokens.json
src/qbo_mcp/qbo_tokens.json
src/qbo_mcp/config/qbo_tokens.json
```

(root file ≈718 bytes — real access/refresh token data, not a placeholder.)

Intuit access/refresh tokens grant full read/write API access to the company
file. They are in git history (notably commit `bc0b868`) and therefore on GitHub.

**Applied:** added ignore rules and `git rm --cached` for all three files
(commit `chore(security): stop tracking QBO OAuth token files`). Working copies
are preserved; the file default is unchanged.

**Still required (owner action):**
1. **Revoke/rotate** the leaked tokens in the Intuit developer console
   (disconnect the app / re-run OAuth) for **both sandbox and production**.
2. If the repo is public or the tokens were ever live, **purge history**
   (`git filter-repo --path qbo_tokens.json --invert-paths`, plus the two `src/`
   paths) and force-push.
3. Consider `chmod 600` on the token file and, ideally, storing tokens in the OS
   keyring / a secrets manager instead of plaintext JSON.

### 🟠 S2 — OAuth `state` is not validated (CSRF)
`oauth_flow.py` starts a local `HTTPServer` and accepts any `code`+`realmId`
redirect. The OAuth `state` parameter is generated by the library but never
checked on callback. On a workstation this is low-to-moderate risk, but it should
validate `state` to prevent a malicious page from injecting a code.

### 🟠 S3 — Verbose global logging
`logging.basicConfig(level=DEBUG)` + `logger.setLevel(DEBUG)` at import time in
`auth.py`, `config/config.py`, `__main__.py`, and root-logger usage means DEBUG
is on by default for the whole process. The MCP transport is stdio, so logs and
any token-adjacent values are user-visible. Recommend INFO default with
`QBO_DEBUG=1` opt-in, and a module logger (`logging.getLogger(__name__)`).

### 🟢 S4 — Good basics
`.env`, `.venv`, caches are ignored; `env.example` is tracked with no secrets;
no hardcoded credentials in source.

## 3. Correctness & reliability

### 🔴 R1 — Default-argument calls fail schema validation (bug)
`generate_profit_loss_report()`, `generate_balance_sheet_report()`,
`generate_cash_flow_report()`, `generate_sales_by_customer_report()`, and
`generate_expenses_by_vendor_report()` are documented as "date omitted →
defaults to current period". But `_generate_*` builds
`{"period": {"start_date": None, "end_date": None}}` and validates **before**
applying defaults. The JSON Schema requires `type: string`, so `None` is rejected:

```
jsonschema.exceptions.ValidationError: None is not of type 'string'
```

Verified locally. Effect: the primary tools return
`{"status": "error", "message": "...JSON Schema validation error..."}` whenever
the caller omits dates. The convenience tools (`get_current_month_pl`, etc.)
pass explicit dates and are unaffected, so this has gone unnoticed.

**Fix:** apply the period defaults first, then validate — or relax the schema to
`["string", "null"]` and only pattern-check non-null values.

### 🟠 R2 — Import-time browser OAuth / import-time side effects
`QBOService.__init__` (executed at import via the module-level `qbo_service`
singleton) calls `run_interactive_oauth` when no tokens exist — blocking on a
browser login **during import**. Also `QBOConfig.__init__` creates/touches the
token file and `config/config.py` raises at import if `QBO_CLIENT_ID`/`SECRET`
are missing. An MCP server should start instantly and fail lazily with a clear
error; auth should be an explicit `--auth` step (the flag already exists).

### 🟠 R3 — Token refresh on every tool call
`get_authenticated_client()` → `ensure_authenticated()` → `auth_client.refresh()`
unconditionally. Access tokens are valid ~60 min, so this performs a network
refresh on every single tool call — needless latency and failure surface.
Recommend refreshing only when the token is near expiry (track `expires_in`).

### 🟡 R4 — Report parsers assume one shape
`_process_balance_sheet_report`, `_process_cash_flow_report`,
`_process_sales_report`, and `_process_expenses_report` all just delegate to
`_process_profit_loss_report`. Balance Sheet / Cash Flow / Sales-by-Customer rows
differ from P&L, so sections/items are likely wrong or empty. Aging parsing
hardcodes ≥6 columns and a fixed bucket order. Recommend per-report parsers, or
return raw QBO JSON plus a thin normalizer.

### 🟡 R5 — No retry/backoff
QBO throttles at ~500 req/min and returns transient 429/5xx. There is no retry,
backoff, or `Retry-After` handling. The rate-limit error codes are not surfaced
in a structured way.

### 🟡 R6 — Duplication & structure
- Seven near-identical `_generate_*` functions and seven near-identical `@mcp.tool()`
  wrappers → a table-driven registry would cut ~200 lines.
- `server.py` uses `from .config import *` / `.auth import *` / `.tools import *`
  (star imports; ruff F403/F405 explicitly ignored).
- `QBOConfig` is a plain class (not `@dataclass`) though typed as one.
- Inconsistent error handling (`get_balance_sheet` logs+raises; siblings wrap in
  `ValueError`; `_ensure_authenticated_and_handle_errors` logs "Auth check
  successful" in a `finally`, even on failure).
